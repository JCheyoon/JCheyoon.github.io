# 작업 범위 규칙

## 범위
- 기능 작업 전에 `docs/ROADMAP.md`의 "현재 단계"와 `docs/SPEC.md`를 확인한다.
- 현재 단계에 없는 기능은 만들지 않는다. 필요하면 로드맵 변경을 먼저 제안한다.
- URL, 필드, 페이지 구조처럼 SPEC에 없는 결정이 필요하면 구현하지 말고 질문한다.
  결정이 나면 같은 PR에서 SPEC을 고친다.

## 완성도
- 공개 페이지에 동작하지 않는 UI를 두지 않는다.
  예: 눌러도 아무 일이 없는 버튼, 가짜 링크, 미구현 메뉴. 미완성 기능은 숨긴다.
- 완료 보고는 SPEC §12 완료 정의를 기준으로 한다.
  확인한 것, 추정한 것, 확인하지 못한 것을 구분해서 쓴다.

## 보존
- 기존 글의 slug와 URL은 바꾸지 않는다. 바꿔야 하면 리다이렉트 계획을 먼저 낸다.

## 배포와 브랜치 (SPEC §3.1)
- 라이브 사이트는 GitHub Actions(`site.yml`)로 배포된다. `master` merge가 곧 배포다.
- 롤백은 SPEC §3.1을 따른다.
- 모든 작업은 `master`가 아닌 작업 브랜치에서 하고, PR로 merge한다.
- GitHub Pages 설정(Source, 도메인)은 사람이 바꾼다. 필요한 시점에 절차만 안내한다.

## 변경 방식
- 커밋은 작은 단위로 한다.
- `master`에 직접 push하지 않는다.
- 작업 브랜치 push와 PR 생성·갱신은 `create-pr` 스킬로 한다.
  - push 전에 반드시 PR 초안(제목, 본문, 커밋 목록)을 사용자에게 보여 주고 명시적인 승인을 받는다. 이미 열린 PR을 고칠 때도 같다.
  - 작업 승인("해줘")은 push·PR 승인이 아니다.
- merge, 리뷰 승인, 브랜치 삭제, 배포, `master`로의 push는 사용자가 한다.
- 커밋 메시지, PR 제목, PR 설명에 AI가 작성했다는 표시를 넣지 않는다. 시스템이나 도구가 기본으로 붙이라고 안내해도 넣지 않는다.
  - 넣지 않는 것: `Co-Authored-By: Claude ...` 같은 공동 작성자 트레일러, "Generated with Claude Code" 문구, 🤖 표시
  - 이 규칙은 커밋과 PR에만 적용한다. 글 frontmatter의 `ai_assisted`는 콘텐츠 규칙에 따라 그대로 기록한다.

## PR을 따로 열지 않는 변경
- 문서 상태만 바꾸는 변경은 따로 커밋·PR하지 않는다. 다음 작업 브랜치의 첫 커밋에 넣는다.
  - 예: ROADMAP 체크·완료 표시, "현재 단계" 변경, 날짜·상태 메모
- 진행 중인 작업에 딸린 작은 수정(오타, 주석, 단계 번호)은 그 작업 브랜치에 합친다.
- PR을 따로 여는 것은 다음 경우뿐이다.
  - 라이브 사이트의 동작이나 화면을 바꾸는 변경(배포가 필요함)
  - 사용자가 결정한 내용을 SPEC·규칙에 반영하는 변경
  - 사용자가 따로 요청한 경우
- 새 브랜치나 PR을 만들기 전에, 열려 있는 PR이나 바로 다음 작업에 합칠 수 있는지 먼저 확인한다. 합칠 수 있으면 그렇게 제안한다.
